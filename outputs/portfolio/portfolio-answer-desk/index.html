01 · VISION

Every leader's portfolio question gets one correct answer, with its sources, in minutes.

Today an analyst searches reports, letters and spreadsheets by hand, and two analysts can return two numbers. With one shared foundation, the chat, the committee pack and the briefing note all ask the same governed metrics.

02 · THE PROBLEM

Three things go wrong today.

1 · You miss routes to a company

Calder Packaging sits behind a fund, a fund of funds, a co-investment and a stake bought second-hand, under three spellings. The write-down is only in a manager letter.

2 · Your pack drifts from last quarter's

Each analyst computes IRR, TVPI, unfunded and the call forecast their own way, as of whatever date the data has.

3 · You miss issues in manager letters

Numbers live in one place, letters in another, and who moved where in someone's head.

03 · THE SOLUTION

The AI picks a governed metric. Code computes and checks every number. You decide what to send.

What it is

A portfolio question desk for an LP's private equity team: chat, a governed dashboard and a briefing-note writer on one data foundation.

What it does

You type a question in plain words. It returns the number, every route, the definition, the date and source of every figure, or a refusal that names who can answer.

What you get

A faster, correct reply to the CIO, a committee pack on last quarter's definitions, and a manager briefing with every issue quoted.

06 · LIMITATIONS

What this doesn't prove yet.

  • Data: synthetic, generated with known answers; real reports are messier than these four layouts.
  • AI: offline, fixed readers stand in for the AI, so the results show what each setup can and can't do, not Claude's error rate. The live run is not yet done.
  • Users: no analyst has used it. The checking times are assumptions; if you recheck half the sourced numbers by hand, the time advantage disappears, the correctness one doesn't.
  • Test set: 60 questions written by the same author as the setups. A held-out world with new spellings scored the same, but no question touched the 11 names left unmatched there.

Main learnings what the build showed

How it's built input, process, output, and how it was evaluated

Input: six synthetic sources with their own rhythm: holdings (daily), call and distribution notices (about weekly), fund reports (quarterly, 40 to 90 days late, four layouts), manager letters, reference data, news every 15 minutes.

Process: documents land as received (bronze), are read into checked fields with bad rows blocked (silver: 26 malformed notices blocked), and become typed tables with the source of every row (gold). The AI reads the question into fixed fields; the semantic layer computes; the graph walks routes and people; a checker blocks any number not computed.

Output: a chat answer, a 3-view committee dashboard with export, a manager briefing note, a read-only SQL notebook.

Evaluation: 60 questions with answers known from the generator, five setups, scored on correctness first, then time to a sendable answer under a stated checking model. A held-out world (another seed, new spellings) scored separately.

Portfolio Answer Desk: Opportunity Analysis

Date: 2026-10-25 Owner: PM (drafted by Claude, run unattended with PM approval) Status: Go

Problem Statement

Senior leaders at a large LP (an investor that commits money to many private equity funds) ask ad hoc portfolio questions. Each answer takes an analyst hours to a day, and two analysts can return two different numbers for the same question.

Current Situation

Sara, a portfolio analyst, answers by hand. She searches fund reports, manager letters and spreadsheets, then adds up what she finds.

A concrete case (labelled hypothetical, synthetic data). Monday 08:10, news says Calder Packaging is restructuring its debt. At 08:12 the CIO asks: "How exposed are we, through which managers, and did we know?" The company sits behind four routes: a fund we committed to, a fund of funds, a co-investment and a fund stake bought second-hand. It appears under three spellings. The write-down sits only in a manager letter from 10 September. Sara finds the direct fund in minutes. Finding the other three routes and the letter takes the rest of the morning, and she may still miss one.

Proposed Solution

One shared data foundation that answers three kinds of request, each through the front end that suits it:

  • For the CIO's event question: a chat assistant. A language model (an AI that reads and writes text) turns the question into a request for governed numbers; code computes them; every number shows its source and as-of date.
  • For the investment committee pack: a governed dashboard where each metric has one definition, an owner and a version, computed as of a set date.
  • For a manager decision: a generated briefing note: the numbers, plus what the manager's letters said, each line cited.

Code checks the AI's work: it can only pick metrics that exist, and it refuses when no definition exists or the asker's role can't see the data.

Solution Overview

States designed (review fix): refusal card (what was asked, why refused, who can answer, "Answer what I can see instead"); "1 letter item not counted, waiting for review" line under any total it affects; empty card for a company we don't hold; offline banner when the AI stand-in answered. Every route shows its own as-of date; sources older than 90 days read "stale"; the first line says "as of mixed dates" when they differ. Each metric carries one plain sentence of what's counted, in US dollars. Sara can add a note that travels with the copied answer. "Copy answer to send" copies the paragraph, routes, sources, as-of dates and the disclaimer. Every screen, copy and export carries "Synthetic data. Not investment advice."

Arms scored: A, B, C, C+ids (C plus an alias table, to test whether the graph earns its place), D. Offline, A gets query expansion from the company reference text and B gets curated views with column notes and parent links, so the baselines are strong, not strawmen.

Four foundations share one synthetic world. Each is paired with the front end that suits each request.

Front ends: chat (request 1), governed dashboard with 3 views (request 2), briefing note (request 3), notebook or SQL page for the data team.

Data: six synthetic sources, each with its own rhythm and as-of date: holdings (daily), capital calls and distributions (notice text, about weekly), quarterly reports (45 to 90 days late, each manager its own layout and spelling), manager letters (whenever, turned into dated events with a confidence; low confidence waits for a person), company reference data (slow-changing, parents), news (every 15 minutes, never a source of numbers).

Stack, decided by measurement after the build (decision docs PAD-01 to PAD-06 in outputs/decisions/): recursive SQL for routes, NetworkX for people links, own YAML semantic layer, bronze, silver and gold in DuckDB 1.4.4, AI picks and code computes. Original plan: (one decision doc each in outputs/decisions/): graph engine (DuckDB recursive SQL, DuckPGQ, NetworkX, archived or server options), semantic layer (own YAML against an established open-source layer), storage layers (bronze, silver, gold in DuckDB), where the AI sits (it picks, code computes).

The pytest gate is a regression gate on the build (pipeline, access, disclaimer, number checker), labelled a mechanism test. It is not the ranking: the ranking is confirmed by the live run.

Success Metrics

Primary: time until Sara has a correct, sourced answer she would send, including checking time. A wrong answer fails, however fast. Checking time is a stated model (assumed): 20 s to read, 5 s per number shown with source and definition, 120 s per number she must verify by hand. Baseline: unobserved; the timed run below measures it. Target: under 10 minutes per question on the winning combination. Sensitivity: half and double the per-number times, and 0%, 50% or 100% of sourced numbers rechecked by hand.

Pre-registered thresholds (set before any run): - Correctness is ranked first, on its own, as counts out of 20 per request. - The graph earns its place only if D beats C+ids (C plus an alias table) by 2 or more correct questions on request 1, or by 2 or more minutes median time. Otherwise the recommendation is C+ids, with the graph kept for teaching. - A live result counts only if all arms get the same model, prompt budget and retries.

Also measured: correctness (number within 0.5%, and routes), latency p50 and p95, cost per answer, freshness, correct refusals, same answer on rerun, build effort (moving parts, lines of code), and results at 10 and 100 times the data.

Guardrail: zero wrong numbers presented as sourced.

Kill criteria: if C or D fails a non-trap question offline, the eval gate blocks the build. If the live run shows the AI picking the wrong metric on more than 5% of questions, the chat front end is removed and the dashboard and briefing note stay.

Rollout Plan

Approach: demo first, on Streamlit Community Cloud, no servers. - Phase 1: offline demo and committed eval results. Passing: all tests pass with no key. - Phase 2: live eval with claude-sonnet-5-5 run locally by the PM (one command). Passing: guardrail holds. - Phase 3 (next, gate before any headline is published): timed human run. 3 to 5 former LP analysts; three arms (manual with documents and spreadsheets, A, the winner); counterbalanced order; a different but equally hard company per arm; questions from all three requests. Record time to "send", numbers reopened, correct or not, would send (yes or no), confidence 1 to 5. One practice session first. Refit the checking-time model from it.

Rollback: if the live run breaks the guardrail, the demo stays offline-only.

Appendix: challenges to the brief (written down, as the brief asks)

  1. The main metric depends on an assumed checking-time model. A foundation that shows sources wins partly by construction. We publish a sensitivity table and report correctness on its own.
  2. Offline A and B are deterministic stand-ins for an AI. They show each mechanism's limits, not Claude's error rate. Live results are a separate, labelled run.
  3. "Graph for company identity" mixes two jobs. Identity matching is a lookup problem an alias table can also solve. We test C plus an alias table, so the graph has to earn its place on routes, not only spellings.
  4. 20 questions per request is small. One question moves a score by 5 points. We report counts, not only shares.
  5. The forecast and plan figures are rules, not truth. For the call forecast, "correct" means "matches the governed rule as of the date", which tests consistency, not foresight.
